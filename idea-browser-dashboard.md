A possible future direction for runny is a lightweight browser-based project dashboard: instead of accidentally serving a directory listing, runny could intentionally expose a local page that scans a chosen projects folder, such as /Users/appleseed/Documents/code, and presents each child folder as a project card. Each card could show what runny can infer about the project: Vite app, static site, Python app, Swift/Xcode prototype, unknown folder, currently running or stopped, active port, PID, and last launch time.

Clicking a project would not simply open the folder’s files. It would ask runny to start or focus the associated development process. For example, clicking a Vite project could run npm run dev, wait for the actual listening port, then open the app URL in a new tab. A static HTML project could start a Python server on an available port. A native iOS project might show “not runnable by runny yet” or offer to reveal it in Finder/Xcode later. Running projects could have Stop, Restart, and Open buttons.

This would turn runny into a small local control plane for personal projects. The terminal TUI would still be useful, but the browser view could become a more visual “front door” for browsing, launching, and revisiting projects without remembering exact folders, ports, or commands. The important distinction is that this should be an intentional dashboard backed by runny’s registry and inference system, not a raw directory listing exposed by accident.
